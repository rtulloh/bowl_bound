## Description

backend/__main__.py and backend/launcher.py separately own LOCAL_HOSTS, port validation, argument definitions, app construction, optional Uvicorn handling and server startup. The newer runner adds resource discovery, versioning, socket reservation and browser lifecycle, while the older module remains a documented supported command with different cwd/static requirements. Two policy implementations make fixes and new flags easy to apply inconsistently. This is a maintainability finding, not evidence that the older API-only mode should be removed.

## Resolution / verification

- Use one small shared parser/binding policy or one runner with explicit source/API-only defaults; keep entry points as thin adapters. Avoid introducing a class hierarchy or generalized launcher framework.
- Preserve existing python -m backend behavior where static assets are optional, and preserve production launcher resource checks, version output, local-only default and readiness behavior.
- Parameterize shared invalid-port/remote-opt-in tests across entry points and retain distinct tests only for intentional resource/browser differences. Document those differences once.
