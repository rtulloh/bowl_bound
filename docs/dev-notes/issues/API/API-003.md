## Description

POST /snap accepts both calls on a game created with human_side=home, and /coach takes human_side in each request body, so a coached game can be driven manually or with alternating sides. Two back-to-back identical /coach requests both return 200 and resolve two plays; the browser's inFlight ref is the only guard. Local solitaire makes this self-cheating only, but the contract is undocumented and would be inherited by any remote use.

## Resolution / verification

- Commit `23129e1` binds each registered game to manual or coached control and the selected human side, including when loading a save. Mismatched and missing control sides are rejected. `/coach` requires `expected_revision`; the command journal position is checked under the game lock, and responses return the next revision. The browser carries the selected side when loading and the revision with each coached turn.
- Test-first evidence: the new API contract cases failed unchanged on unbound controls, duplicate requests and fingerprint mismatch. Validation passed: 84 API tests; 33 focused frontend tests; production frontend build; Ruff lint and formatting; and `git diff --check`. Coverage includes manual `/snap` rejection on coached games, missing/alternating sides, sequential and concurrent duplicate coach posts, exact/oversized 16 KiB command bodies, load at `MAX_SAVE_BYTES` and one byte over, and changed team fingerprints through the API.
- Commit `8fdf6cf` updates the terminal/API continuation integration test to load and decide under one bound human side, then send the API's current revision with the coached request. The two side-parameterized continuation cases pass.
- Awaiting owner play-test before closure.
